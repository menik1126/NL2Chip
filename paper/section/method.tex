\section{Method}
\label{sec:method}

We present \textsc{Sparkle}, an end-to-end framework that translates natural language hardware specifications into formally verifiable, synthesizable hardware designs. The key insight is that by targeting a dependently-typed hardware description language embedded in Lean~4 rather than generating Verilog directly, the LLM agent receives rich compile-time feedback---type errors, width mismatches, and formal verification failures---that guides iterative refinement toward correct-by-construction hardware.

\subsection{Overview}
\label{sec:overview}

Figure~\ref{fig:pipeline} illustrates the complete pipeline. Given a natural language specification $\mathcal{S}$ and an optional reference Verilog implementation $\mathcal{V}_{\text{ref}}$, our system produces a formally described hardware design through the following stages:

\begin{enumerate}[leftmargin=*,itemsep=1pt,topsep=2pt]
    \item \textbf{LLM Code Generation.} A coding agent $\mathcal{A}$ translates $\mathcal{S}$ into Sparkle HDL (Lean~4) code $\mathcal{L}$, using few-shot examples from a verified benchmark library and iterative error correction.
    \item \textbf{Compilation \& Extraction.} The Lean~4 compiler type-checks $\mathcal{L}$ and extracts synthesizable SystemVerilog $\mathcal{V}$ via the \texttt{\#synthesizeVerilog} metaprogram.
    \item \textbf{Functional Verification.} $\mathcal{V}$ is simulated against reference testbenches to verify functional correctness.
    \item \textbf{Physical Synthesis.} $\mathcal{V}$ is synthesized and placed-and-routed using OpenROAD with the SkyWater 130nm PDK, yielding PPA (Power, Performance, Area) metrics.
    \item \textbf{PPA Optimization.} The agent receives PPA feedback and iteratively optimizes the architecture while preserving functional correctness.
\end{enumerate}

\subsection{Sparkle HDL: Hardware in Lean~4}
\label{sec:sparkle_hdl}

Sparkle HDL is a domain-specific language embedded in Lean~4 that describes hardware using \texttt{Signal} combinators. A signal \texttt{Signal dom $\alpha$} represents a synchronous stream of values of type $\alpha$ under clock domain \texttt{dom}. Semantically, a signal is a function from discrete time steps to values: $\texttt{Signal dom } \alpha \triangleq \mathbb{N} \to \alpha$. This denotational semantics enables both cycle-accurate simulation (by evaluating the function) and formal reasoning (by proving properties over the function). The embedding in Lean~4 provides four properties that make it uniquely suited as an LLM compilation target for chip architecture.

\paragraph{Type-Safe Bit Widths.}
Lean~4's dependent type system encodes bit widths at the type level via \texttt{BitVec $N$}. Width mismatches---a pervasive source of silent bugs in Verilog---become compile-time errors. For example, adding a 4-bit and an 8-bit signal without explicit extension is rejected by the type checker, providing immediate feedback to the LLM agent. This is critical for chip architecture: a datapath width error in a pipelined multiplier or an address bus mismatch in a memory controller would silently propagate through Verilog synthesis but is caught \emph{before compilation completes} in Sparkle.

\paragraph{Structural Safety via the Signal Monad.}
Combinational logic forms a directed acyclic graph enforced by the \texttt{Signal} monad; state feedback is only possible through explicit register primitives (\texttt{Signal.register}, \texttt{Signal.loop}), making combinational loops impossible by construction. Lean's exhaustive pattern matching prevents unintended latches---a common synthesis hazard in Verilog's \texttt{always} blocks. For sequential circuits, Sparkle provides an imperative \texttt{Signal.circuit} macro that desugars into \texttt{Signal.loop} and \texttt{Signal.register} calls, enabling a natural description of pipelines and state machines:
\begin{small}
\begin{verbatim}
def counter {dom : DomainConfig} : Signal dom (BitVec 8) :=
  Signal.circuit do
    let count <- Signal.reg 0#8
    count <~ count + 1#8
    return count
\end{verbatim}
\end{small}
This compiles to a single \texttt{always\_ff} block with proper clock and reset handling. More complex architectures---finite state machines, multi-stage pipelines, memory-mapped controllers---compose from the same primitives. For instance, an FSM is expressed as a \texttt{Signal.loop} over state with \texttt{Signal.mux} for transition logic, where the type system ensures all state encodings have consistent bit widths.

\paragraph{Memory and Datapath Primitives.}
Sparkle provides synthesizable memory primitives that map directly to SRAM/BRAM in physical synthesis: \texttt{Signal.memory} (synchronous read with 1-cycle latency), \texttt{Signal.memoryComboRead} (combinational read for register files), and \texttt{Signal.memoryWithInit} (pre-loaded ROM/RAM). Address and data widths are encoded in the type signature, so a memory access with a mismatched address width is a compile-time error. Combined with the standard arithmetic operators overloaded on \texttt{Signal dom (BitVec $N$)}, these primitives allow the LLM agent to describe complete chip architectures---ALUs, register files, caches, and interconnects---within a single type-checked Lean~4 file.

\paragraph{Formal Verification.}
Designers (or the LLM agent) can state and prove theorems about the hardware directly in Lean~4. Because signals have a denotational semantics as functions over time, properties can be stated as standard Lean theorems. For instance, a counter's initial value and increment behavior:
\begin{small}
\begin{verbatim}
theorem counter_starts_at_zero :
    (counter.atTime 0) = 0#8 := by rfl

theorem counter_increments (n : Nat) :
    (counter.atTime (n+1)) = (counter.atTime n) + 1#8 := by
  simp [counter, Signal.register]; rfl
\end{verbatim}
\end{small}
For architecture optimization, equivalence proofs between a specification and an optimized implementation provide machine-checked correctness certificates:
\begin{small}
\begin{verbatim}
theorem equiv (input : Signal dom (BitVec 3)) :
    optimized input = spec input := by
  unfold optimized spec; rfl
\end{verbatim}
\end{small}
This capability is essential for the PPA optimization loop (\S\ref{sec:ppa_opt}), where the agent must ensure that architectural transformations preserve functional correctness across all possible inputs---a guarantee that simulation-based testing alone cannot provide.

\subsection{Compilation and Verilog Extraction}
\label{sec:compilation}

A central design goal of Sparkle is that the \emph{compiler is the verifier}: every Lean~4 build invocation simultaneously type-checks the hardware description, enforces structural invariants, and extracts synthesizable RTL. This section details the compilation pipeline that transforms a Lean~4 source file into backend-ready SystemVerilog.

\paragraph{Lean~4 Type Checking.}
When the LLM agent writes a Sparkle design to \texttt{Generated/\{prob\_id\}.lean} and invokes \texttt{lake build}, Lean's elaborator resolves all dependent types, verifies bit-width consistency across the entire design, and checks that all pattern matches are exhaustive. A single \texttt{lake build} invocation thus catches three classes of bugs that would silently pass Verilog synthesis: (1)~width mismatches between connected signals, (2)~incomplete case analysis in multiplexer or FSM logic, and (3)~type-level violations such as using a boolean where a bit vector is expected. The compiler error messages are structured and localized, enabling the LLM agent to apply targeted fixes rather than guessing.

\paragraph{Intermediate Representation.}
Upon successful type checking, the \texttt{\#synthesizeVerilog} metaprogram lowers the \texttt{Signal} combinator graph into Sparkle's intermediate representation (IR). The IR is a netlist-like structure that preserves the hierarchical module boundaries and signal names from the Lean source, maintaining a 1:1 structural correspondence between the Lean code and the generated Verilog. Unlike Chisel's FIRRTL, which aggressively transforms and renames signals during lowering, Sparkle's IR retains human-readable names, making the generated SystemVerilog inspectable by both the LLM agent and human designers.

\paragraph{Design Rule Check (DRC).}
Before Verilog emission, the IR passes through a built-in Design Rule Check that enforces backend-friendly RTL conventions inspired by industry standards (e.g., STARC guidelines). The primary check is \emph{registered output enforcement}: the DRC verifies that all module outputs are driven directly by flip-flops rather than combinational logic. Unregistered outputs cause critical path explosion across module boundaries and make static timing analysis (STA) unpredictable. When the DRC detects a violation, it emits a structured warning:
\begin{small}
\begin{verbatim}
[DRC] Module 'alu': output 'out' is not driven by a register
\end{verbatim}
\end{small}
This feedback is actionable for the LLM agent: it can insert a \texttt{Signal.register} at the output to resolve the violation. The DRC thus serves as an early physical-awareness check, reducing the number of synthesis-P\&R iterations needed to achieve timing closure.

\paragraph{SystemVerilog Emission.}
The final stage emits clean, synthesizable SystemVerilog from the DRC-validated IR. Clock and reset signals are automatically inserted into the module port list. Registers are emitted as \texttt{always\_ff} blocks with synchronous reset. Combinational logic is emitted as \texttt{assign} statements or \texttt{always\_comb} blocks. The generated code is compatible with all major EDA tools (Yosys, Synopsys Design Compiler, Cadence Genus) and simulation tools (Verilator, Icarus Verilog). A \texttt{TopModule} wrapper is automatically generated to map Sparkle's port naming conventions to standard testbench interfaces, enabling seamless integration with the VerilogEval reference testbenches used in our evaluation pipeline.

\subsection{LLM Coding Agent}
\label{sec:agent}

The coding agent $\mathcal{A}$ is an LLM equipped with tool-use capabilities that iteratively writes, compiles, and debugs Sparkle HDL code. We instantiate $\mathcal{A}$ using Claude with the following components:

\paragraph{System Prompt.}
The agent receives a structured system prompt containing: (1)~the Sparkle HDL syntax reference, including the \texttt{Signal} API, type system, and core operators; (2)~design patterns for combinational logic, sequential circuits, and finite state machines; (3)~critical rules encoding common pitfalls (e.g., ``use \texttt{Signal.mux} instead of \texttt{if-then-else}''); and (4)~a prescribed workflow for iterative development.

\paragraph{Tool Suite.}
The agent has access to seven tools: \texttt{bash} (execute shell commands with 120s timeout), \texttt{read\_file}, \texttt{write\_file}, \texttt{edit\_file} (surgical string replacement), \texttt{grep}, \texttt{glob}, and \texttt{list\_directory}. These tools enable the agent to explore the codebase, read benchmark examples, write Lean code, invoke the compiler, and analyze error messages.

\paragraph{Few-Shot Retrieval.}
Before generating code, the agent reads from a library of 10 verified benchmark implementations spanning combinational circuits, sequential logic, and FSMs. These serve as in-context examples that demonstrate correct Sparkle HDL patterns and naming conventions.

\paragraph{Iterative Compile-Fix Loop.}
The agent follows a multi-turn conversation protocol:
\begin{enumerate}[leftmargin=*,itemsep=0pt,topsep=2pt]
    \item Read the natural language specification and reference Verilog.
    \item Identify similar benchmark examples via \texttt{grep}/\texttt{glob}.
    \item Write an initial Lean~4 implementation to \texttt{Generated/\{prob\_id\}.lean}.
    \item Invoke \texttt{lake build} and parse compiler diagnostics.
    \item If compilation fails, analyze the error (type mismatch, unknown identifier, syntax error), apply a targeted fix via \texttt{edit\_file}, and retry.
    \item Once compilation succeeds, verify the extracted SystemVerilog.
\end{enumerate}
The agent is allowed up to $T$ turns (default $T{=}40$) per problem. Each turn consists of one LLM inference followed by zero or more tool invocations.

\subsection{Automated Evaluation Pipeline}
\label{sec:eval_pipeline}

Once the agent produces a candidate Lean~4 file, the evaluation pipeline assesses it through a sequence of increasingly stringent checks:

\begin{enumerate}[leftmargin=*,itemsep=1pt,topsep=2pt]
    \item \textbf{Lean Compilation.} \texttt{lake build Generated.\{prob\_id\}} verifies type correctness and triggers Verilog extraction.
    \item \textbf{SystemVerilog Extraction.} The build output is parsed to extract the generated \texttt{.sv} file. A \texttt{TopModule} wrapper is automatically generated to map Sparkle's port naming conventions to the reference testbench interface.
    \item \textbf{Lint Check.} Verilator or Icarus Verilog performs static analysis to catch synthesis-incompatible constructs.
    \item \textbf{Functional Simulation.} The design is simulated against the VerilogEval reference testbench using Icarus Verilog. The testbench applies input vectors and compares outputs cycle-by-cycle, reporting the number of mismatches out of total samples.
    \item \textbf{Logic Synthesis.} Designs passing simulation are synthesized using Yosys targeting the SkyWater 130nm HD standard cell library (\texttt{sky130\_fd\_sc\_hd}) via the OpenROAD Flow Scripts (ORFS) Docker environment. This yields gate-level netlists and initial PPA estimates.
    \item \textbf{Place \& Route.} The synthesized netlist undergoes floorplanning, placement, clock tree synthesis, routing, and finishing in OpenROAD, producing a GDSII layout. Static timing analysis (STA) reports worst negative slack (WNS) across multiple PVT corners (SS/TT/FF).
\end{enumerate}

The pipeline is fully automated and containerized: synthesis and P\&R run inside a Docker container with pre-installed ORFS and the sky130 PDK, ensuring reproducibility.

\subsection{PPA Optimization Loop}
\label{sec:ppa_opt}

For designs that pass functional simulation and synthesis, we employ a closed-loop PPA optimization strategy that is one of the central contributions of this work. The key idea is that by coupling the LLM agent with quantitative physical design feedback, we transform hardware optimization from a manual, expert-driven process into an automated, iterative refinement loop. The agent receives concrete metrics about the physical characteristics of its design and uses this information to make informed architectural decisions.

\paragraph{PPA Metrics.}
After each synthesis and place-and-route iteration, the pipeline extracts a comprehensive PPA vector $\mathbf{p}_i = (\text{area}_i, \text{power}_i, \text{WNS}_i, \text{cells}_i)$ from the OpenROAD reports. Area is measured in $\mu\text{m}^2$ from the Yosys synthesis statistics (e.g., ``Chip area for module: 45.04~$\mu\text{m}^2$''), decomposed into sequential and combinational contributions. Power is reported in $\mu\text{W}$ from OpenROAD's power analysis across multiple PVT corners. Worst Negative Slack (WNS) is extracted from static timing analysis across slow-slow (SS), typical-typical (TT), and fast-fast (FF) corners, indicating how far the design is from meeting timing at the target clock frequency. Cell count provides a proxy for design complexity and routing congestion.

\paragraph{Feedback Construction.}
At each optimization iteration $i$, a structured feedback message is constructed for the agent containing: (1)~the current PPA metrics $\mathbf{p}_i$ with human-readable formatting; (2)~the complete optimization history $\{\mathbf{p}_0, \ldots, \mathbf{p}_i\}$ so the agent can identify trends; (3)~a delta analysis highlighting which metrics improved or degraded relative to the previous iteration; and (4)~targeted optimization guidance based on the dominant bottleneck. For area-dominated designs, the guidance suggests reducing intermediate signals, merging operations, or using more compact encodings. For timing-critical designs, it suggests pipelining long combinational paths or restructuring mux chains. This structured feedback transforms raw EDA tool output into actionable intelligence that the LLM can reason about.

\paragraph{Optimization Procedure.}
Let $\mathbf{p}_i$ denote the PPA vector after iteration $i$. The optimization proceeds for $K$ iterations (default $K{=}3$):

\begin{enumerate}[leftmargin=*,itemsep=1pt,topsep=2pt]
    \item \textbf{Agent Resume.} The agent resumes from its prior conversation state with the PPA feedback appended, preserving full context of the design decisions made so far. This is critical: the agent retains knowledge of the Sparkle HDL patterns it used, the type errors it resolved, and the architectural choices it made, enabling informed optimization rather than blind search.
    \item \textbf{Architecture Modification.} The agent modifies the Lean~4 source to produce an optimized variant. Common transformations include: replacing parallel datapaths with serialized versions to reduce area, merging cascaded multiplexers into lookup tables, eliminating redundant registers, and restructuring arithmetic expressions to reduce critical path depth.
    \item \textbf{Re-compilation and Type Checking.} The modified design is re-compiled through Lean~4, ensuring that the optimization did not introduce type errors, width mismatches, or structural violations. This is a key advantage over optimizing Verilog directly: the type system catches optimization-induced bugs immediately.
    \item \textbf{Re-evaluation.} The design passes through the full pipeline (compilation $\to$ simulation $\to$ synthesis $\to$ P\&R), producing updated PPA metrics $\mathbf{p}_{i+1}$.
    \item \textbf{Improvement Assessment.} An iteration is considered an improvement if any metric improves by ${>}5\%$ without any metric degrading by ${>}20\%$:
    \begin{equation}
        \text{improved}(\mathbf{p}^*, \mathbf{p}_{i+1}) = \exists\, m: \frac{p^*_m - p_{i+1,m}}{|p^*_m|} > 0.05 \;\wedge\; \forall\, m: \frac{p_{i+1,m} - p^*_m}{|p^*_m|} < 0.20
    \end{equation}
    where $\mathbf{p}^*$ is the global best PPA vector across all iterations. This asymmetric threshold allows the agent to explore trade-offs (e.g., slightly increasing area to significantly improve timing) while preventing catastrophic regressions.
    \item \textbf{Rollback on Failure.} If simulation fails after an optimization attempt---indicating the transformation broke functional correctness---the Lean source is rolled back to the pre-iteration version and the loop continues with the next iteration, rather than terminating early. This exhaustive strategy ensures the agent explores the full optimization budget.
\end{enumerate}

After all $K$ iterations complete, the globally best design (by PPA) is restored as the final output. The entire loop is fully automated: no human intervention is required between iterations.

\paragraph{Formal Equivalence in the Optimization Loop.}
A unique capability enabled by Sparkle's embedding in Lean~4 is that the agent can produce formal equivalence proofs between the original and optimized architectures as part of the optimization loop. After each architectural transformation, the agent can attempt to prove:
\begin{small}
\begin{verbatim}
theorem opt_equiv (input : Signal dom (BitVec N)) :
    optimized_v2 input = original input := by
  unfold optimized_v2 original; simp [Signal.mux, ...]; rfl
\end{verbatim}
\end{small}
When such a proof succeeds, it provides a machine-checked guarantee that the optimization preserves functional correctness for \emph{all} possible inputs---not just the test vectors in the simulation testbench. This is particularly valuable for optimizations that restructure control logic or change state encodings, where simulation coverage may be insufficient to catch corner-case divergences.

\subsection{Architecture Exploration}
\label{sec:arch_explore}

For designs where the optimization space is large, we support an architecture exploration mode. The agent generates $C$ distinct architectural candidates (default $C{=}3$), each implementing the same specification with different micro-architectural choices (e.g., parallel vs.\ serial datapaths, different encoding schemes, tree vs.\ chain reduction). Each candidate is independently evaluated through the full pipeline, and the best is selected by PPA metrics.

When formal verification is enabled, the agent additionally produces equivalence proofs between the original specification and each optimized architecture:
\begin{small}
\begin{verbatim}
theorem arch_equiv (input : Signal dom (BitVec N)) :
    arch_optimized input = spec input := by
  unfold arch_optimized spec; simp [Signal.mux, ...]
\end{verbatim}
\end{small}
This provides machine-checked guarantees that architectural optimizations preserve functional correctness---a property that simulation alone cannot ensure for all possible inputs.
