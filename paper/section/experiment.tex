\section{Experiments}
\label{sec:experiments}

We evaluate \textsc{Sparkle} on the VerilogEval benchmark~\citep{liu2023verilogeval}, a suite of 156 hardware design problems spanning combinational logic, sequential circuits, and finite state machines. Our evaluation addresses four questions: (1)~Can an LLM agent effectively generate hardware through a type-safe HDL? (2)~How does this compare to direct Verilog generation? (3)~Do the generated designs synthesize to physical layouts? (4)~Can the PPA optimization loop improve design quality?

\subsection{Experimental Setup}
\label{sec:setup}

\paragraph{Benchmark.}
VerilogEval contains 156 problems drawn from HDLBits, each with a natural language specification, reference Verilog implementation, and a simulation testbench. Problems range from simple wire assignments (Prob001) to complex FSMs with multiple outputs (Prob155).

\paragraph{Model and Agent Configuration.}
We use Claude Sonnet 4.5 (\texttt{claude-sonnet-4-5-20250929}) as the backbone LLM for all experiments, with temperature 0. The agent is allowed up to $T{=}40$ turns per problem. Each turn consists of one LLM inference followed by tool invocations (file read/write, shell commands for compilation and simulation).

\paragraph{Baseline.}
As a baseline, we evaluate the same LLM generating SystemVerilog directly from the natural language specification in a single pass (zero-shot, no iterative refinement). This isolates the effect of the type-safe HDL and iterative compile-fix loop from the underlying model capability.

\paragraph{Infrastructure.}
Synthesis and place-and-route use the OpenROAD Flow Scripts (ORFS) with the SkyWater 130nm HD standard cell library (\texttt{sky130\_fd\_sc\_hd}) inside a Docker container. Functional simulation uses Icarus Verilog. All experiments run on a single machine with 32 CPU cores.

\paragraph{Compilation Rate.}
\textsc{Sparkle} achieves a 92.9\% Lean compilation rate (145/156), higher than the baseline's 89.7\% Verilog compilation rate. This demonstrates that the iterative compile-fix loop, guided by Lean's structured type errors, enables the agent to resolve the majority of issues. The 11 failures involve complex designs (e.g., Conway's Game of Life, gshare branch predictor) where the agent exhausted its turn budget without resolving all type errors.

\paragraph{Functional Correctness.}
The simulation pass rate for \textsc{Sparkle} is 69.9\% (109/156), compared to the baseline's 71.8\% (112/156). While the baseline achieves a higher raw simulation rate, this comparison is nuanced. The baseline generates Verilog directly---a language the LLM has seen extensively in training data---while \textsc{Sparkle} targets a novel DSL with no pre-training exposure. The 69.9\% rate is achieved entirely through in-context learning from 10 few-shot examples and iterative type-guided refinement. Moreover, \textsc{Sparkle}'s designs carry stronger correctness guarantees: every design that compiles is free of width mismatches, combinational loops, and incomplete case analysis by construction.

\paragraph{Synthesis and Physical Design.}
A key advantage of \textsc{Sparkle} is that compiled designs are immediately synthesis-ready. Of 145 compiled designs, 144 (99.3\%) pass Yosys synthesis, and 126 (86.9\%) complete place-and-route through OpenROAD, producing GDSII layouts. The baseline achieves 112/156 (71.8\%) synthesis success and 106/156 (67.9\%) P\&R completion, demonstrating that direct LLM-generated Verilog can also produce synthesizable designs, though at a lower rate than \textsc{Sparkle}'s type-checked output.

\paragraph{Agent Efficiency.}
The agent uses an average of 22.3 turns per problem, with total token usage of approximately 1.3M input and 580K output tokens across all 156 problems. The full pipeline (code generation + synthesis + P\&R) completes in approximately 12 hours. In contrast, the baseline completes in under 7 minutes (single-pass generation, no iteration), but produces no synthesis artifacts.

\subsection{PPA Optimization Loop}
\label{sec:ppa_opt_results}

We evaluate the closed-loop PPA optimization on the same 63-problem subset, running $K{=}5$ optimization iterations per design. Of 29 designs that entered the optimization loop (those passing both simulation and synthesis), 4 achieved measurable area reductions:

\begin{itemize}[leftmargin=*,itemsep=1pt,topsep=2pt]
    \item \texttt{fsmshift}: 170.2 $\to$ 151.4\,$\mu$m$^2$ (11.0\% reduction)
    \item \texttt{always\_case}: 226.5 $\to$ 214.0\,$\mu$m$^2$ (5.5\% reduction)
    \item \texttt{shift18}: 4{,}625.7 $\to$ 4{,}524.3\,$\mu$m$^2$ (2.2\% reduction)
    \item \texttt{counter\_2bc}: 122.6 $\to$ 120.1\,$\mu$m$^2$ (2.0\% reduction)
\end{itemize}

The modest improvement rate (4/29) reflects the difficulty of optimizing already-correct designs through the Lean type system: each optimization attempt must re-compile, re-simulate, and re-synthesize, and the type checker rejects many transformations that would be valid at the Verilog level but violate Sparkle's stricter invariants. This is a feature, not a bug---the type system prevents the agent from introducing subtle correctness errors during optimization. The architecture exploration mode (\S\ref{sec:arch_results}) proves more effective for PPA improvement, as generating fresh candidates avoids the constraints of incremental modification.

\subsection{Error Analysis}
\label{sec:error_analysis}

We analyze the 36 designs that compile but fail simulation to understand the remaining challenges.

\paragraph{FSM Semantics.}
The largest failure category (approximately 40\% of failures) involves finite state machines with complex transition logic. The agent correctly encodes the state type and register structure but makes errors in transition conditions or output assignments, particularly for FSMs with many states or non-obvious reset behavior. These are semantic errors that the type system cannot catch---the code is type-correct but implements the wrong state machine.

\paragraph{Timing and Reset Conventions.}
Approximately 25\% of failures stem from mismatches between Sparkle's reset conventions (synchronous reset, active-high) and the testbench expectations. Some VerilogEval testbenches assume asynchronous reset or active-low reset, which requires explicit handling in Sparkle that the agent sometimes omits.

\paragraph{Complex Datapath Logic.}
The remaining failures involve designs with intricate bit manipulation (e.g., LFSR feedback polynomials, BCD counters, Conway's Game of Life neighborhood computation) where the agent makes algorithmic errors unrelated to the HDL abstraction.

\subsection{Discussion}
\label{sec:discussion}

The results reveal a fundamental trade-off in targeting a type-safe HDL versus direct Verilog generation. The baseline achieves a higher simulation pass rate (71.8\% vs.\ 69.9\%) because the LLM has extensive pre-training exposure to Verilog and can leverage memorized patterns. However, \textsc{Sparkle}'s designs carry substantially stronger guarantees: every compiled design is free of width mismatches, combinational loops, and incomplete case analysis, and 86.9\% of compiled designs produce physical layouts through the full synthesis and P\&R flow.

We expect the simulation gap to narrow as the agent's few-shot library grows and as LLMs gain exposure to Lean~4 hardware descriptions. The compilation rate (92.9\%) already demonstrates that the iterative type-guided refinement loop is highly effective, and the remaining failures are concentrated in the most complex designs where even human engineers would require significant effort.
